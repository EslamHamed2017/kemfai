## Dependency and execution rules

Role keys used on every task below: `P` = Primary implementer/owner, `B` = Backup, and `R` = independent reviewer/approver. A named acceptance or release owner is a distinct non-implementer role, not the task implementer.

1. IDs are exactly T159–T211, sequentially numbered.
2. T159–T176 are test/meta-evidence only and precede runtime implementation.
3. T177 is the first runtime implementation and directly depends on every task T159–T176.
4. Green claims cannot use mocks, interception, screenshots, responses alone, skips, retries, flaky/partial/transformed evidence, or survivor tolerance.
5. The exact required check is `accounting-foundation-owned-live`; exact-head means the candidate commit SHA, not a branch or earlier SHA.
6. Before T177 begins, T176 must persist read-only proof that this check exists, is required by main branch protection, and is green on the exact graph-review head containing the commissioned graph identity (or a formally re-commissioned graph-review head). Any absence, non-green result, protection drift, base-main drift, or graph-content drift blocks runtime implementation.
7. T159–T175 must produce a complete fail-closed red-evidence manifest before T176 can pass. Every implementation-driving test record includes its task ID and test path, exact command, graph blob OID and SHA-256 digest, exit status, discovered test count, expected failure assertion and observed failure reason. Placeholder, already-green, undiscovered, skipped, or wrong-reason failures block; each positive behavior test must be observed red for its intended missing behavior unless T176 records a specific independently reviewed reason that the test is meta/negative-only and is not expected to fail.
8. T177–T207 may be developed only on an isolated feature branch. No Story 4 runtime implementation may merge into main, develop, or another shared/integration branch until T208–T211 have completed in order for the exact candidate head.
9. Every runtime task T177–T195 is an independently reviewable, non-production vertical slice across Browser UI→Next BFF→Nest→Odoo→tenant audit, with the smallest customer-visible state and its automated tests. Component work may occur inside a slice, but no Odoo-only, API-only, or frontend-only task may be accepted as complete. Every state-changing slice includes its minimum human review and explicit confirmation UI; slices without a positive UI action carry their denial, recovery, read, or disabled state through the same boundaries. T196–T198 are cross-slice acceptance gates, not implementation slices. Independent slices may execute in parallel after their stated prerequisites.
